# Design Steps

## Ambiguity review

- [x] Clarify duplicate concrete-var status transitions, not only repeated failing/erroring snapshots: if a var first publishes a failure artifact and a later completion callback for the same var is `:pass` or `:unknown`, specify whether the earlier `.edn` file and successful-path state are removed, retained, or otherwise reconciled. The current rules say only failing/erroring entries receive files, the latest completed snapshot wins, and successful completion-time files are not rewritten during final reconciliation, but they do not define this transition.
- [x] Pin the incremental/final diagnostic metadata contract: define the allowed `:phase` keyword value(s), whether `:failed-entry-count` counts unique artifacts still missing after reconciliation, which ordering selects `:first-failing-var`/root cause, and whether a failed retry reports the original incremental exception or the reconciliation exception. “A phase distinguishing ... where useful” and “when derivable” leave the structured outcome under-specified for implementation and regression tests.
- [x] Clarify the outcome when an incremental artifact write fails and the runner then throws before final reconciliation: state whether the runner-error outcome also carries `:scry.cli/diagnostic-error` for the still-missing callback-known artifact, how its failed-entry count/phase are represented, and which stderr diagnostics are emitted in addition to the runner-error message/results-directory pointer.
- [x] Define temporary-file cleanup after catchable serialization/write/move failures and after normal reconciliation: specify whether the sink must best-effort delete its temporary file immediately, may leave ignored temporary files until the next run clears the directory, or follows different rules for incremental and reconciliation failures. The design only explicitly assigns next-run cleanup to temporary files left by uncatchable termination.
- [x] Clarify the Kaocha `post-test` ordering guarantee relative to all active project/plugin `post-test` hooks, not only `capture-output`: state where the adapter-owned hook must run so its entry is final if another hook can subsequently alter result counts, assertion history, or output, or explicitly bound “final” to state after the capture-output plugin. Using the same transformer alone does not prevent incremental/final drift if later hooks mutate the leaf.
- [x] Define “CLI-side callback failures” precisely for the composed callback: state whether containment applies only to incremental sink serialization/filesystem failures or also to terminal progress writer/flush failures, and identify the outcome/diagnostic behavior for each. The broad observational-callback statement currently implies all callback failures are contained, while the detailed containment contract discusses only the sink.

## Inconsistency review

- [x] Reconcile the callback cardinality contract with duplicate-callback semantics. The unified contract says `:progress-callback` “fires once after each concrete var reaches its completion boundary,” and required Kaocha coverage says each leaf triggers one callback, but the identity section says the same concrete var may be “completed more than once” and later completion callbacks replace its artifact. State explicitly that callback cardinality is once per concrete-var *execution/completion event*, not once per var identity per run, so repeated execution is compatible with latest-snapshot behavior.
- [x] Reconcile “the latest completed snapshot wins” with “a successfully published completion-time snapshot is authoritative and is not overwritten merely because the final bulk result is available.” For a duplicate failing/erroring var, define whether final reconciliation must retain the latest successful callback snapshot even when the canonical result vector contains multiple entries for that identity in execution order, and ensure canonical-order `:result-files` does not return the same path more than once. As written, the latest-wins/no-duplicates rule can conflict with reconciliation against per-entry canonical order.
- [x] Reconcile the runner-error result-shape change with the API-doc trigger. The design intentionally requires catchable runner errors to preserve non-empty `:result-files` while `:result nil`/`:summary nil`, but Scope mentions generated API docs only “if the callback docstring contract changes.” The public `scry.cli/run` docstring/generated `doc/API.md` describes `:result-files` and diagnostic outcomes, so require that public outcome documentation to cover runner-error preservation regardless of whether the callback docstring changes; keep the design’s explicit shape exception unchanged.

## Plan review — ambiguity review

- [x] Define which exceptions after sink creation use the sink's exception-path snapshot. The plan specifies preserved files for a “catchable runner exception,” while `run-cli` currently has one broad catch covering runner invocation, canonical-result validation, summary/seed output, result-file writing, and stderr diagnostics, and the design more broadly promises runner-error artifact preservation. Pin whether malformed/missing canonical results and post-run output failures preserve already published `:result-files` and unresolved incremental diagnostics like an exception thrown by `run-normalized`; if valid canonical entries exist before a post-run failure, also state whether reconciliation is attempted or only the no-reconciliation snapshot is used.
- [x] Specify how callback-known concrete filenames participate in synthetic filename collision reservation during final reconciliation. `result-file-assignments` currently reserves concrete filenames found in the final canonical vector, but a successful or unresolved callback-only concrete identity may be absent from that vector. Without an explicit reservation rule, a synthetic assignment can select the same path and overwrite the incremental concrete artifact (for example, concrete `foo/suite-error-1` versus the first synthetic `:error` in namespace `foo`), contradicting callback-only preservation and deterministic collision behavior.
- [x] Replace “run ... repeatedly enough to rule out timing flakiness” in Slice 6 with a deterministic completion criterion: pin a repetition count (and whether it applies to the whole focused Kaocha slice or only the interruption regression), plus the expected handling when the child-process interruption path is unsupported and the synchronization fallback is used. Otherwise different implementers cannot tell when this required step is complete.

## Plan review — inconsistency review

- [x] Reconcile the retry-source rule for repeated concrete identities. `design.md` requires reconciliation to retry a failed latest callback snapshot from the *matching* latest failing/erroring canonical entry and to use the retained callback snapshot when no matching final entry exists, whereas `plan.md` and Slice 3 say to use the latest failing/erroring canonical entry whenever one exists. For duplicate executions, an unmatched canonical entry can represent an older execution or different mutable completion snapshot. Define how callback generations correspond to canonical occurrences, then make the plan and steps preserve the design's matching/fallback rule.
- [x] Remove or qualify `plan.md`'s claim that “No implementation blocker or unresolved design decision is known” while this task has unchecked plan-review follow-ups. Restore such a readiness statement only after the ambiguity and inconsistency items are resolved, so the plan does not simultaneously declare implementation-ready closure and record unresolved contractual choices.
- [x] Carry the resolved runner-abort diagnostic contract consistently into the plan and executable verification steps. `design.md` requires an unresolved incremental publication followed by a runner exception to emit the bounded failure-diagnostics lines (including first var/root cause when derivable), then the normal runner-error line and a results-directory pointer only if another artifact survived. The plan/steps currently mention attached diagnostic metadata and the surviving-file pointer but do not require this stderr behavior or a combined unresolved-write/runner-exception regression, allowing the previously resolved design requirement to be omitted during implementation.

## Plan re-review — inconsistency review

- [ ] Reconcile the diagnostic phase boundary between `design.md` and the resolved plan. The design says `:final-result-file-reconciliation` applies after any normal runner return and `:incremental-result-file-writing` only when a runner exception prevents reconciliation, while the plan and Slice 4 assign the incremental phase to missing or malformed canonical vectors even though the runner returned normally. Define the boundary in one way across design, plan, and steps, and pin the phase used when validated reconciliation itself throws before producing a complete reconciled snapshot.
- [ ] Reconcile completion-generation tracking in the plan with the Slice 2 state checklist. The plan requires a monotonically advancing completion generation for every concrete callback so callbacks can be ordinally matched with same-identity canonical occurrences, but Slice 2 names only the required failure generation and says only failing/erroring callbacks advance it. Require separate all-callback occurrence/generation tracking—including pass/unknown callbacks—without turning those non-failing callbacks into artifact requirements, so Slice 3's ordinal matching can be implemented as specified.
