# Design Steps

## Ambiguity review

- [ ] Clarify duplicate concrete-var status transitions, not only repeated failing/erroring snapshots: if a var first publishes a failure artifact and a later completion callback for the same var is `:pass` or `:unknown`, specify whether the earlier `.edn` file and successful-path state are removed, retained, or otherwise reconciled. The current rules say only failing/erroring entries receive files, the latest completed snapshot wins, and successful completion-time files are not rewritten during final reconciliation, but they do not define this transition.
- [ ] Pin the incremental/final diagnostic metadata contract: define the allowed `:phase` keyword value(s), whether `:failed-entry-count` counts unique artifacts still missing after reconciliation, which ordering selects `:first-failing-var`/root cause, and whether a failed retry reports the original incremental exception or the reconciliation exception. “A phase distinguishing ... where useful” and “when derivable” leave the structured outcome under-specified for implementation and regression tests.
- [ ] Clarify the outcome when an incremental artifact write fails and the runner then throws before final reconciliation: state whether the runner-error outcome also carries `:scry.cli/diagnostic-error` for the still-missing callback-known artifact, how its failed-entry count/phase are represented, and which stderr diagnostics are emitted in addition to the runner-error message/results-directory pointer.
- [ ] Define temporary-file cleanup after catchable serialization/write/move failures and after normal reconciliation: specify whether the sink must best-effort delete its temporary file immediately, may leave ignored temporary files until the next run clears the directory, or follows different rules for incremental and reconciliation failures. The design only explicitly assigns next-run cleanup to temporary files left by uncatchable termination.
- [ ] Clarify the Kaocha `post-test` ordering guarantee relative to all active project/plugin `post-test` hooks, not only `capture-output`: state where the adapter-owned hook must run so its entry is final if another hook can subsequently alter result counts, assertion history, or output, or explicitly bound “final” to state after the capture-output plugin. Using the same transformer alone does not prevent incremental/final drift if later hooks mutate the leaf.
- [ ] Define “CLI-side callback failures” precisely for the composed callback: state whether containment applies only to incremental sink serialization/filesystem failures or also to terminal progress writer/flush failures, and identify the outcome/diagnostic behavior for each. The broad observational-callback statement currently implies all callback failures are contained, while the detailed containment contract discusses only the sink.

## Inconsistency review

- [ ] Reconcile the callback cardinality contract with duplicate-callback semantics. The unified contract says `:progress-callback` “fires once after each concrete var reaches its completion boundary,” and required Kaocha coverage says each leaf triggers one callback, but the identity section says the same concrete var may be “completed more than once” and later completion callbacks replace its artifact. State explicitly that callback cardinality is once per concrete-var *execution/completion event*, not once per var identity per run, so repeated execution is compatible with latest-snapshot behavior.
- [ ] Reconcile “the latest completed snapshot wins” with “a successfully published completion-time snapshot is authoritative and is not overwritten merely because the final bulk result is available.” For a duplicate failing/erroring var, define whether final reconciliation must retain the latest successful callback snapshot even when the canonical result vector contains multiple entries for that identity in execution order, and ensure canonical-order `:result-files` does not return the same path more than once. As written, the latest-wins/no-duplicates rule can conflict with reconciliation against per-entry canonical order.
- [ ] Reconcile the runner-error result-shape change with the API-doc trigger. The design intentionally requires catchable runner errors to preserve non-empty `:result-files` while `:result nil`/`:summary nil`, but Scope mentions generated API docs only “if the callback docstring contract changes.” The public `scry.cli/run` docstring/generated `doc/API.md` describes `:result-files` and diagnostic outcomes, so require that public outcome documentation to cover runner-error preservation regardless of whether the callback docstring changes; keep the design’s explicit shape exception unchanged.
